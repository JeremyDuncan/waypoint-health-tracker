## Deployment, persistence and restore

The smoke test copies source without `.env`, master/credentials files, installed bundles/modules, local databases, logs, generated assets or browser artifacts. It builds via Compose and starts an initially empty named volume, waiting for a healthy database-backed `/up`. It then:

1. Creates two accounts with the documented email-free CLI, and signs in over HTTP in the explicitly configured loopback trial mode.
2. Logs synthetic readings around **23:55 / 00:05 America/New_York**, actual injections and a separate journal through real HTTP endpoints with CSRF tokens. Confirms custom range boundaries and event dates, with no fabricated injection weight values.
3. Exports JSON and reimports it twice through upload, preview and commit endpoints. Compares exact personal records. The second account cannot read the first account's entries, import preview or exported records.
4. Runs both browser projects against the production container.
5. Takes a consistent online backup while the app is running, verifies integrity, and copies the snapshot off the volume.
6. Recreates the source container and verifies fresh login, exact exported records and counts.
7. Streams the backup through the documented `bin/restore -` command into a **second, fresh Compose project/volume**, starts it, verifies integrity and compares all counts, exact personal records and preferences. Existing credentials sign in successfully; restored sessions are revoked.
8. Resets a password with the CLI, verifies the old session is invalid and signs in again.

Final expected/restored counts: **2 accounts, 11 weigh-ins, 3 actual injections, 1 journal entry**. These counts include the HTTP fixture plus both browser flows and CSV imports. Repeated imports preserve counts. All isolated smoke containers/volumes are removed after the run.
