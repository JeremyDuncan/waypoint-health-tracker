# Personal data format, version 1

Files are UTF-8. CSV uses a header row and RFC 4180 quoting (commas/newlines inside fields are quoted). Download examples from Settings or see `docs/examples/`. CSV exports are intended for data tools: import fields as text in spreadsheets, especially notes that might begin with formula characters.

## Stable IDs and time

Every saved record has a UUID, exported as `id`, stable across edits and exports. IDs are scoped to the account; another account may import the same personal export into its own records. Server database IDs are internal and not exported. Event `occurred_at` is ISO 8601 with seconds, optional microseconds, and an explicit UTC offset (`2026-11-02T00:05:42.123456-05:00` or `Z`). The original event timestamp string and entered weight/unit are retained. Display dates and chart filters use your Settings time zone, independent of the server's operating-system zone. Day notes use `local_date` (`YYYY-MM-DD`) without a time or invented offset. A time zone change changes which day an instant appears on; it does not move a journal date.

## CSV exports

- `weights.csv`: `id,occurred_at,value,unit`. `value` is a decimal with up to four fractional places; `unit` is `lb` or `kg`.
- `injections.csv`: `id,occurred_at,dose,site,side,notes`. `dose` is Zepbound mg (2.5, 5, 7.5, 10, 12.5, 15); optional site is `Abdomen`, `Thigh`, or `Upper arm`; side is `Left` or `Right`. These are actual logs, never plans.
- `day_notes.csv`: `id,local_date,notes,metrics`. `metrics` is a quoted JSON object. Keys carry the measurement unit: `appetite`/`severity` (0–10), `side_effects` (text), `waist_cm`, `systolic`/`diastolic` (mmHg), `resting_heart_rate` (bpm), `sleep_hours` (hours). Blank optional values are absent from the object.

CSV import in Settings supports **weight history**. Restore injection/journal records with full JSON. Map date/time, weight, optional unit and stable-ID columns. No unit is inferred from a number. ISO mode requires a timestamp with offset. For date-only files, explicitly choose YYYY-MM-DD, MM/DD/YYYY, or DD/MM/YYYY and a UTC offset; preview assigns **local noon**. This does not claim to recover a scale's missing measurement time. Split files around daylight-saving offset changes. Other timestamp formats should be normalized to ISO 8601 before upload. Invalid/ambiguous values have row errors, with CSV line numbers starting at 2 after the header.

Without an ID column, a deterministic UUID is derived from the normalized timestamp, value and unit. Identical source rows import once. Changed rows without IDs cannot reliably be identified as edits: they appear as creates. Retain stable IDs for future transfers and review every preview. Two source rows with an identical timestamp, value and unit and no IDs are deliberately treated as one; use distinct IDs if those are separate measurements.

## Renpho Health CSV

Choose **Renpho Health CSV** in Settings, or upload with the generic weight CSV option for automatic detection. Supported exports have separate `Date` (`YYYY.MM.DD`) and `Time` (`HH:MM:SS`) columns and one `Weight(lb)` or `Weight(kg)` column. A synthetic example is in `docs/examples/renpho-weights.csv`.

The preview combines date/time to preserve the reading's exact second and uses the unit explicitly stated in the column header. Renpho provides no UTC offset: the preview initially uses your account's time zone and lets you change it before committing. Each reading receives the correct historical daylight-saving offset for that chosen zone. Invalid dates, nonexistent spring-forward times and ambiguous repeated fall-back times are reported by row. For an ambiguous reading, normalize that row to an ISO timestamp with its actual offset and use the generic CSV importer; the app does not guess which occurrence happened.

Renpho imports **weight readings only**. BMI, body composition estimates and Remarks are not imported. The preview makes that limitation explicit. It does not create injections or journals from scale measurements.

Because Renpho's `No.` sequence changes between exports, stable IDs are derived from the local date/time of the source reading, not its row number or weight. Reordered or overlapping re-exports are duplicates. Changes to an already imported reading, its unit or its interpreted time zone become conflicts, so edits are never silently overwritten. Two different readings sharing the exact same source second are flagged as a conflict rather than guessed apart. All preview/commit, row validation and account-scoping rules apply.

## JSON document

The export has `schema: "waypoint-health.personal"`, `version: 1`, `exported_at`, `preferences`, `metric_definitions`, and `records`. `records` contains arrays `weights`, `injections`, and `day_notes` with the same fields as CSV, with `metrics` as a JSON object. Decimal weights/doses are strings to preserve precision. `metric_definitions` contains all supported definitions including labels, units and limits. Preferences contain `preferred_unit`, IANA `time_zone`, `enabled_metrics`, and `reminder_at` (an ISO timestamp or null). Reminder timestamps describe plans only. JSON is the complete personal transfer format. Legacy Hearth exports with schema `hearth.personal` and version 1 remain importable, with the same duplicate and conflict checks.

The v1 definitions are fixed and validated on import; custom metric definitions are not supported. Unrecognized schema versions, definitions and fields are rejected, rather than losing information. Unknown metrics, impossible dates, excess weight precision and invalid doses are validation errors.

Preferences now also contain the optional `weight_goal` field: null when no goal is set, or an object with exactly `mode`, `value`, `unit`, `start_date`, `low`, and `high`. `mode` is `target` or `maintenance`; `unit` is `lb` or `kg`; `start_date` is an explicit local `YYYY-MM-DD`. A target has a positive decimal-string `value` and null `low`/`high`. Maintenance has positive decimal-string `low`/`high` (low ≤ high) and a null `value`. Weights allow up to four decimal places. Milestones and maintenance-day counts are derived from actual readings and are not separate records. Legacy v1 files without `weight_goal` remain supported and leave an existing goal unchanged when applying their preferences. A present null explicitly clears the goal when preferences are applied. Backup status and appointment-report files are excluded from personal exports.

## Preview and commit

The optional `chart_preferences` preference is an object with up to two page keys, `overview` and `injections`; `{}` selects defaults. A saved page contains its complete settings. Both use `range` (`7`, `30`, `90`, `365`, `all`, or `custom`, as strings). Only custom ranges include `from` and `to` as inclusive local ISO dates. Overview also has `mode` (`raw`, `weekly`, `monthly`) and boolean `trend`, `weight`, `injections`, and `notes`. Injections has `mode` (`calendar`, `aligned`), `site` (`all`, `unknown`, or a listed injection site), `side` (`all`, `unknown`, `Left`, `Right`), `dose` (`all` or a listed decimal-string mg dose), and `grouping` (`site_side`, `site`). Legacy files without `chart_preferences` leave existing selections unchanged. A present object replaces those selections only when imported preferences are explicitly applied; an empty object resets both pages. These settings contain no record IDs or authentication data and are included in full server backups.

The optional preference `height_cm` is a positive decimal string up to 300 (centimeters), with up to four stored decimal places, or null when unset. Height entered in inches in the goal editor is converted using 2.54 cm per inch. Legacy v1 files without this field leave an existing height unchanged; a present null clears it when preferences are applied. Height belongs to the personal profile rather than the goal, so clearing a goal does not clear height. BMI is derived from current weight and height and is not a separate measurement record.

Uploads are limited to 5 MB and previews expire after an hour. Preview data is kept in your private server database, never a shared upload directory. Old previews are removed on the next upload; expired previews cannot be opened or committed. The preview lists all rows with creates, duplicates, conflicts and errors. Same ID and values: duplicate; same ID with different values: conflict. An existing journal date with a different ID is also a conflict. Duplicates are skipped. Any error or conflict blocks the whole transaction. Preferences are displayed separately and applied only with the checked confirmation in the commit form.

Commit revalidates the file inside a database write transaction, catching edits made since preview. Repeated commits and repeated uploads are safe. Imports never overwrite existing records. Reconcile conflicts in the source file, or deliberately delete/reconcile an existing record through its day details before retrying. This is not a merge tool.

Personal exports exclude login email, password/password hash, sessions, throttle state, preview uploads, and server secrets. A full SQLite backup includes account authentication data and is a different workflow.
